# Feature Specification: 商品庫存管理與防止超賣

**Feature Branch**: `010-product-inventory`

**Created**: 2026-07-12

**Status**: Draft

**Input**: User description: "在 \"商品管理\" 頁面新增庫存，且要確保新增訂單時不會超賣"

## Clarifications

### Session 2026-07-12

- Q: 「不會超賣」需要涵蓋外部顧客端 App 建立的訂單嗎？ → A: 僅後台——本次只保證後台新增/編輯訂單不超賣；App 端防線列為未來功能，App 既有下單流程不得中斷。
- Q: 商品的「庫存」欄位應代表什麼？ → A: 剩餘可售計數器——管理員直接設定「還可賣幾件」，下單扣減、刪單回補，列表顯示單一剩餘數字（非「檔期總量＋推算剩餘」模式）。
- Q: 出貨（結單清除群組）時庫存應如何處理？ → A: 不回補、不重設——剩餘庫存延續到下一檔期，由管理員視需要自行調整。
- Q: 後台新增／編輯訂單的商品選單中，售完（庫存 0）商品如何呈現？ → A: 標示「售完」且不可選取（未追蹤庫存商品不受影響）；送出時的庫存檢查仍為最終防線。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 後台維護商品庫存 (Priority: P1)

管理員在「商品管理」頁面為每個商品設定與調整「庫存數量」：新增商品時可填入庫存，編輯商品時可修改庫存，商品列表直接顯示各商品目前剩餘庫存。庫存為選填——未設定庫存的商品視為「不限量」（不追蹤庫存），行為與現行完全相同；庫存為 0 的商品顯示「售完」標示。

**Why this priority**: 庫存數字是防止超賣的前提資料；即使先不做下單檢查，讓管理員看得到、改得動各商品剩餘量本身就有備貨管理價值。

**Independent Test**: 在商品管理頁新增一個商品並填入庫存 10，列表顯示剩餘 10；編輯改為 5 後列表同步更新；填入負數或小數被阻擋；留空儲存後顯示為不限量。

**Acceptance Scenarios**:

1. **Given** 管理員在商品管理頁新增商品，**When** 於表單填入庫存 20 並儲存，**Then** 商品建立成功且列表顯示剩餘庫存 20。
2. **Given** 既有商品庫存為 20，**When** 管理員編輯商品將庫存改為 8，**Then** 儲存成功且列表顯示 8。
3. **Given** 管理員於庫存欄位輸入 -3、2.5 或文字，**When** 送出，**Then** 儲存被阻擋並提示庫存須為非負整數。
4. **Given** 商品未設定庫存（留空），**When** 檢視商品列表，**Then** 顯示「不限量」標示，且該商品下單不受庫存限制。
5. **Given** 商品庫存被扣減至 0，**When** 檢視商品列表，**Then** 顯示醒目的「售完」標示。

---

### User Story 2 - 新增訂單時防止超賣 (Priority: P2)

管理員在後台新增訂單時，系統逐品項檢查有追蹤庫存的商品：任一品項的訂購數量超過該商品目前剩餘庫存，整筆訂單即被拒絕，並明確提示是哪個商品不足、目前還剩多少。訂單成立的同時扣減對應庫存；檢查與扣減是同一個不可分割的動作，因此即使多人同時搶下最後的庫存，也絕不會賣超。

**Why this priority**: 這是本功能的最終目的——「新增訂單時不會超賣」。依賴 US1 的庫存資料存在後才有意義，故排在其後。

**Independent Test**: 將某商品庫存設為 3，成立一筆訂購 2 件的訂單成功且庫存變 1；再嘗試訂購 2 件被拒絕並看到「剩餘 1」的提示；改訂 1 件成功且列表顯示售完。

**Acceptance Scenarios**:

1. **Given** 商品甲庫存 5，**When** 新增一筆含甲 3 件的訂單，**Then** 訂單成立且甲的剩餘庫存變為 2。
2. **Given** 商品甲剩餘庫存 2，**When** 新增一筆含甲 3 件的訂單，**Then** 整筆訂單被拒絕、庫存維持 2，並提示「甲庫存不足（剩餘 2）」。
3. **Given** 一筆訂單含商品甲（庫存足夠）與商品乙（庫存不足），**When** 送出，**Then** 整筆訂單被拒絕，甲與乙的庫存皆不變（不得部分成立、部分扣減）。
4. **Given** 商品甲剩餘庫存 1，**When** 兩筆各訂購 1 件甲的訂單幾乎同時送出，**Then** 恰好一筆成立（庫存變 0），另一筆被拒絕並提示庫存不足。
5. **Given** 商品乙未設定庫存（不限量），**When** 新增含乙任意數量的訂單，**Then** 訂單照常成立，不做庫存檢查也不扣減。
6. **Given** 商品甲剩餘庫存 0，**When** 管理員在新增或編輯訂單的商品選單中瀏覽，**Then** 甲顯示「售完」標示且不可選取（不限量商品不受此限制）。

---

### User Story 3 - 編輯／刪除訂單同步調整庫存 (Priority: P3)

出貨前訂單是可編輯的工作資料：管理員在訂單中加品項或增加數量時，套用與新增訂單相同的庫存檢查與扣減；減少數量、移除品項或刪除整筆訂單時，對應庫存自動回補。出貨（結單）代表商品實際售出交付，不回補庫存。

**Why this priority**: 沒有這一層，US2 的防超賣會失真——改單增量可繞過檢查、刪單後庫存數字虛減。但其價值建立在 US1、US2 之上。

**Independent Test**: 商品甲庫存 5，成立含甲 3 件的訂單（剩 2）；編輯訂單把甲改為 1 件，剩餘變 4；再改為 6 件被拒絕（剩餘 4 不足以再加 5）；刪除整筆訂單後剩餘回到 5。

**Acceptance Scenarios**:

1. **Given** 訂單含商品甲 3 件、甲剩餘庫存 2，**When** 編輯訂單將甲增為 4 件，**Then** 編輯成功且甲剩餘庫存變為 1（僅扣增加的 1 件）。
2. **Given** 訂單含商品甲 3 件、甲剩餘庫存 0，**When** 編輯訂單將甲增為 4 件，**Then** 整次編輯被拒絕並提示甲庫存不足，訂單與庫存皆不變。
3. **Given** 訂單含商品甲 3 件，**When** 編輯訂單將甲減為 1 件，**Then** 編輯成功且甲剩餘庫存回補 2。
4. **Given** 訂單含商品甲 2 件，**When** 刪除整筆訂單，**Then** 甲剩餘庫存回補 2。
5. **Given** 群組內有含商品甲的訂單，**When** 管理員對該群組執行出貨（結單清除），**Then** 甲的剩餘庫存不回補（商品已實際售出）。

---

### Edge Cases

- 併發下單搶最後庫存：檢查與扣減為單一不可分割動作，任何併發情境下庫存永不為負、成立量永不超過設定量。
- 一筆訂單含多個品項而其中一項不足：整筆拒絕，所有品項的庫存皆不變（不得部分成立）。
- 同一筆訂單同一商品出現在多個品項行（若可能）：以合計數量對剩餘庫存檢查。
- 管理員可隨時把庫存改成任意非負整數（含 0 與低於已下訂量的值）：庫存語意是「剩餘可售數量」，調整不回溯影響既有訂單。
- 商品刪除：其庫存隨商品一併移除；既有訂單品項行維持快照（名稱、單價、小計）不受影響。
- 未設定庫存（不限量）的商品：完全不受檢查與扣減影響，行為與現行一致；既有商品上線後預設不限量。
- 庫存欄位由「有值」改為「留空」：商品轉為不限量，之後的訂單異動不再檢查與扣減。
- 出貨（結單）不回補庫存；剩餘庫存延續到下一檔期，由管理員自行調整。
- 外部顧客端 App 建立的訂單不套用本檢查（不在本次範圍），其既有下單流程不得因本功能中斷。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每一商品 MUST 可設定「庫存數量」屬性，值為非負整數；未設定（留空）表示不限量（不追蹤庫存）。
- **FR-002**: 商品管理頁 MUST 於新增與編輯商品表單提供庫存欄位，並於商品列表顯示各商品目前剩餘庫存；不限量商品顯示對應標示，庫存 0 顯示售完標示。
- **FR-003**: 管理員輸入的庫存值 MUST 驗證為非負整數，格式不符時阻擋並提示明確錯誤；管理員可隨時調高、調低（含 0）或清空（轉為不限量）。
- **FR-004**: 新增訂單時，系統 MUST 逐品項檢查追蹤庫存的商品：任一品項訂購數量超過剩餘庫存時，整筆訂單 MUST 被拒絕，且 MUST 明確提示不足的商品名稱與目前剩餘數量。
- **FR-005**: 訂單成立 MUST 同步扣減對應商品的剩餘庫存，且庫存檢查與扣減 MUST 為不可分割的單一動作（原子），確保任何併發下單情境下庫存不會為負、不會超賣。
- **FR-006**: 庫存不足導致的拒絕 MUST 不產生任何部分效果：不得成立部分品項、不得扣減任何庫存。
- **FR-007**: 編輯訂單（新增品項、增加數量）MUST 套用與新增訂單相同的檢查與扣減（僅就淨增加量檢查）；減少數量、移除品項或刪除整筆訂單 MUST 回補對應商品的庫存。
- **FR-008**: 出貨（結單清除群組）MUST NOT 回補庫存。
- **FR-009**: 未設定庫存（不限量）之商品 MUST 不受檢查與扣減影響，下單行為與現行一致。
- **FR-010**: 本功能 MUST NOT 中斷外部顧客端 App 既有的下單流程（該端的防超賣不在本次範圍）。
- **FR-011**: 後台新增／編輯訂單的商品選單 MUST 將剩餘庫存 0 的商品標示為「售完」且不可選取（未追蹤庫存之商品不受影響）；此為介面防呆，送出時的檢查（FR-004、FR-005）仍為最終防線。

### Key Entities

- **商品**: 既有實體；新增「庫存數量」屬性——非負整數、可不設定（＝不限量），語意為「目前剩餘可售數量」：訂單成立扣減、刪單/減量回補、出貨不回補、管理員可隨時直接調整。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 任一有庫存上限的商品，在包含併發下單的任何情境下，成立訂單的累計訂購量永不超過管理員設定的庫存量（超賣事件為 0 件）。
- **SC-002**: 管理員在商品管理頁的單一表單操作內即可完成任一商品的庫存設定或調整，列表立即反映最新剩餘量。
- **SC-003**: 每一次因庫存不足被拒的下單或改單，100% 顯示不足商品的名稱與目前剩餘數量。
- **SC-004**: 訂單刪除、減量或移除品項後的庫存回補正確率 100%（回補量恰等於釋出量），無虛減或虛增。

## Assumptions

- 庫存語意為「剩餘可售數量」的計數器：下單扣減、刪單/減量回補、出貨不回補；每檔期的備貨量由管理員自行設定與調整（系統不在出貨時自動歸零或重設）。
- 未設定庫存＝不限量：既有商品上線後一律預設為不限量，行為不變，由管理員視需要逐一啟用庫存追蹤（無需一次性回填）。
- 防超賣的範圍是本後台的訂單新增與編輯；外部顧客端 App 的下單流程不在本次範圍（庫存資料共用同一資料層，該端日後可沿用同一規則）。
- 不需要「保留／購物車鎖定」機制：庫存僅於訂單成立、編輯、刪除時變動。
- 低庫存提醒、庫存異動紀錄（audit log）不在本次範圍。
