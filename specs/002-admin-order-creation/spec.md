# Feature Specification: 後台新增訂單與來源標籤

**Feature Branch**: `002-admin-order-creation`

**Created**: 2026-06-28

**Status**: Draft

**Input**: User description: "訂單管理頁面新增 \"新增訂單\" 按鈕，以實現在後台也能新增訂單，且需要支援標籤功能，可以選擇 \"FB\" 或是 \"Line\""

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 後台手動建立訂單 (Priority: P1)

管理員在訂單管理頁面點擊「新增訂單」按鈕，填入客戶資料、取貨方式、商品與數量後送出，系統即在訂單清單中新增一筆訂單，與顧客端建立的訂單並列管理、可一同匯出結單。

**Why this priority**: 這是本功能的核心價值——讓透過電話、私訊等非顧客端管道收到的訂單也能進入同一套訂單流程，否則這些訂單無法被結單與匯出。

**Independent Test**: 不依賴標籤功能即可單獨測試：開啟新增訂單表單、填入一筆自取訂單並送出，確認該訂單出現在對應縣市/地點的清單中、總額正確、可被展開檢視明細，並能隨該分組一起結單匯出。

**Acceptance Scenarios**:

1. **Given** 管理員在訂單管理頁面，**When** 點擊「新增訂單」按鈕，**Then** 顯示新增訂單表單，可輸入客戶姓名、電話、取貨方式、商品明細與備註。
2. **Given** 管理員已填妥一筆自取訂單（選定取貨點、至少一項商品與數量），**When** 送出表單，**Then** 系統建立該訂單、回到清單並可在對應縣市/地點查得該筆訂單。
3. **Given** 管理員選擇宅配並填入宅配地址，**When** 送出表單，**Then** 系統建立宅配訂單，於「宅配」分組可查得。
4. **Given** 訂單含多項商品，**When** 送出表單，**Then** 系統依各商品目前單價與促銷計算每項小計與訂單總額，並快照保存於該訂單明細。
5. **Given** 表單缺少必填欄位（如未填客戶姓名或未加任何商品），**When** 嘗試送出，**Then** 系統阻擋送出並提示需補齊的欄位。

---

### User Story 2 - 標記訂單來源 (FB / Line) (Priority: P2)

管理員在新增訂單時為訂單選擇來源標籤「FB」或「Line」，以記錄此訂單從哪個社群管道收到；標籤在訂單清單中可見，方便辨識與後續對帳。

**Why this priority**: 來源標籤提升管理與對帳效率，但訂單建立本身（P1）即使沒有標籤也能交付價值，故列為次優先。

**Independent Test**: 可單獨測試：建立訂單時選擇「Line」，送出後於訂單清單該筆訂單顯示「Line」標籤；建立另一筆選「FB」者顯示「FB」標籤。

**Acceptance Scenarios**:

1. **Given** 管理員在新增訂單表單，**When** 檢視來源欄位，**Then** 可在「FB」與「Line」兩個選項中擇一。
2. **Given** 管理員選擇「FB」並送出訂單，**When** 於訂單清單檢視該訂單，**Then** 顯示「FB」來源標籤。
3. **Given** 訂單由顧客端（外部 App）建立、未指定來源標籤，**When** 於訂單清單檢視，**Then** 該訂單來源標籤顯示為預設值「網站」，系統不報錯。

---

### Edge Cases

- 取貨點清單為空時，新增「自取」訂單應如何處理？（無可選取貨點時不允許建立自取訂單，並提示先建立取貨點。）
- 商品清單為空或某商品在送出當下已被刪除時，明細應如何處理？（送出前以目前商品資料為準；找不到的商品不可加入。）
- 同一筆訂單重複加入同一商品時，視為各自一列或合併數量？（預設合併為單一明細列並加總數量。）
- 新增自取訂單時的「取貨號碼牌」如何決定？（沿用既有約定：每取貨點各自遞增，宅配無號碼。）
- 數量輸入 0 或負數、總額為負時，系統必須拒絕。
- 表單送出過程中網路失敗時，不可建立半筆訂單（明細與訂單須一致）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 訂單管理頁面 MUST 提供「新增訂單」按鈕，點擊後開啟新增訂單表單。
- **FR-002**: 新增訂單表單 MUST 可輸入客戶姓名（必填）、電話（選填）、備註（選填）。
- **FR-003**: 表單 MUST 支援選擇取貨方式為「自取」或「宅配」；選「自取」時須指定既有取貨點，選「宅配」時須填入宅配地址。
- **FR-004**: 表單 MUST 可加入一項以上商品並指定各商品數量（數量為正整數），且至少需有一項商品才能送出。
- **FR-005**: 系統 MUST 於建立訂單時，依各商品「目前」的單價與促銷規則計算每項小計與訂單總額，並將單價、數量、促銷與小計以快照方式保存於訂單明細（與顧客端建立的訂單一致，確保歷史不可變）。
- **FR-006**: 表單 MUST 提供訂單來源標籤欄位，可選「FB」或「Line」（亦可保留預設「網站」）。
- **FR-007**: 訂單清單 MUST 顯示每筆訂單的來源標籤；未指定來源者（如顧客端建立的訂單）顯示為預設值「網站」。
- **FR-014**: 訂單來源標籤 MUST 有預設值「網站」；任何未明確指定來源的訂單（含顧客端外部 App 建立者）皆以「網站」為來源。
- **FR-008**: 系統 MUST 在送出前驗證必填與格式（客戶姓名非空、取貨方式對應欄位齊全、至少一項商品、數量為正整數、總額非負），未通過時阻擋送出並提示。
- **FR-009**: 新增的訂單 MUST 與顧客端建立的訂單一視同仁，能在對應縣市/地點或宅配分組被查詢、展開檢視明細，並隨該分組一起結單匯出與清除。
- **FR-010**: 為「自取」訂單建立時，系統 MUST 依既有約定為其指派取貨號碼牌（每取貨點各自遞增）；宅配訂單無號碼牌。
- **FR-011**: 當無任何可用取貨點時，系統 MUST 不允許建立「自取」訂單並提示管理員先建立取貨點。
- **FR-012**: 訂單建立 MUST 為原子操作：訂單主檔與其明細須同時成功，任一失敗則不留下部分資料。
- **FR-013**: 來源標籤匯出至結單 CSV 時 MUST 一併輸出該欄位（未指定者輸出「網站」）。

### Key Entities *(include if feature involves data)*

- **訂單 (Order)**: 一筆顧客訂購紀錄。屬性含客戶姓名、電話、取貨方式、取貨點或宅配地址、取貨號碼牌、備註、總額、建立時間，並新增「來源標籤」（FB / Line，可為空）。與訂單明細為一對多。
- **訂單明細 (Order Item)**: 訂單中的單項商品，快照保存商品名稱、單價、數量、促銷與小計。
- **來源標籤 (Source Tag)**: 標示訂單收單管道的標記，值為「網站」（預設）、「FB」、「Line」；未指定時為「網站」。
- **取貨點 (Pickup Spot)**: 既有實體，自取訂單須關聯一個取貨點。
- **商品 (Product)**: 既有實體，提供建立訂單時可選的商品、目前單價與促銷。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員可在 90 秒內完成一筆含 3 項商品的新增訂單（從點擊「新增訂單」到送出成功）。
- **SC-002**: 後台新增的訂單 100% 出現在對應分組清單中，且總額與明細小計與輸入一致。
- **SC-003**: 後台新增的訂單可與顧客端訂單一同被結單匯出，匯出檔案中該訂單資料完整無遺漏，且含正確來源標籤。
- **SC-004**: 每筆後台新增的自取訂單皆取得唯一的取貨號碼牌（同一取貨點內不重複）。
- **SC-005**: 缺漏必填或格式錯誤的送出 100% 被攔截並提示，且不會產生任何部分（半筆）訂單資料。

## Assumptions

- 「標籤功能」指訂單的「來源管道標籤」，值為「網站」（預設）、「FB」、「Line」；主要供後台新增訂單時選擇與清單辨識使用。
- 來源標籤有資料庫層級預設值「網站」；後台新增訂單時管理員可改選「FB」或「Line」，未改即為「網站」。
- 顧客端（外部 App）建立的訂單不設定來源標籤，故既有訂單與未來顧客端訂單皆套用預設值「網站」。
- 後台新增訂單沿用既有訂單資料結構與結單/匯出流程，不另建獨立的訂單管理介面。
- 建立訂單時以商品「目前」的單價與促銷為準計算並快照，與顧客端下單行為一致（符合「訂單歷史不可變」原則）。
- 自取訂單的取貨號碼牌沿用既有寫入端約定（每取貨點各自遞增、撞號重試），宅配訂單無號碼牌。
- 本功能僅限通過授權的後台管理員使用（沿用既有後台授權機制）。
- UI 文案為繁體中文（zh-TW），與現有後台一致。

## Dependencies

- 既有「取貨點」資料（自取訂單需可選取貨點）。
- 既有「商品」資料與促銷規則（計算明細小計與總額）。
- 既有「結單/匯出（CSV）」流程（新增訂單需可被既有流程涵蓋）。
