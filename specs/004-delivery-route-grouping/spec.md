# Feature Specification: 後台依「送貨路線」分組（取代縣市分組）

**Feature Branch**: `004-delivery-route-grouping`

**Created**: 2026-06-30

**Status**: Draft

**Input**: User description: "功能：後台依「送貨路線」分組（取代縣市分組）— 業主依固定送貨路線配送而非縣市；後台訂單統計、訂單管理篩選、結單改以路線分組。新增路線管理（增/改名/刪，名稱唯一，有取貨點時禁刪）；取貨點歸屬單一路線（未指定者歸「未分路線」），可調整路線內顯示順序；路線訂單統計取代縣市統計；訂單管理以路線篩選（含未分路線、宅配）；結單以整條路線為單位匯出 CSV，下載成功後才清除。前台選點與訂單寫入機制不變。"

## Clarifications

### Session 2026-06-30

- Q: 訂單統計改為「路線 + 日期區間」查詢、兩者擇一必填。當只給日期、沒選路線時，交叉表要如何分組？ → A: 全部取貨點為列，依 `sort_order` 排序（跨所有路線，列出該日期區間內有自取訂單的取貨點）。
- Q: 日期區間的欄位與預設值要如何呈現？ → A: 起訖兩個日期欄位，預設起＝訖＝今天（可改為任意區間）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立與維護送貨路線 (Priority: P1)

管理員在後台新增一條送貨路線、為它命名，並把實際會在同一趟車次配送的（可能跨多個縣市的）取貨點指派到這條路線上。日後可改名或在不再使用時刪除路線。

**Why this priority**: 路線是本功能所有後台作業（統計、篩選、結單）的分組依據。沒有路線資料與取貨點歸屬，其餘功能都無從運作，因此這是最小可行基礎。

**Independent Test**: 可獨立測試 — 新增一條路線、把多個跨縣市取貨點指派給它、改名、嘗試刪除（被擋）、移除取貨點後成功刪除；全程不需要任何訂單資料即可驗證。

**Acceptance Scenarios**:

1. **Given** 後台無任何路線, **When** 管理員新增名為「A 線」的路線, **Then** 該路線出現在路線清單中且可被指派取貨點。
2. **Given** 已有「A 線」, **When** 管理員嘗試新增另一條同樣名為「A 線」的路線, **Then** 系統拒絕並提示名稱重複。
3. **Given** 三個分屬不同縣市的取貨點, **When** 管理員把它們都指派到「A 線」, **Then** 這三個取貨點在所有後台分組檢視中都被視為同一組（A 線）。
4. **Given** 「A 線」底下仍有取貨點, **When** 管理員嘗試刪除「A 線」, **Then** 刪除被阻擋並顯示說明原因的錯誤訊息（仍有取貨點）。
5. **Given** 「A 線」底下的取貨點已全部移除或改派, **When** 管理員刪除「A 線」, **Then** 刪除成功，該路線不再出現。

---

### User Story 2 - 以路線檢視商品需求量並結單交給司機 (Priority: P1)

管理員選定一條路線後，看到該路線上每個取貨點對每項商品的訂購數量交叉表與各商品總量，以便備貨；接著以整條路線為單位匯出一份涵蓋線上所有取貨點訂單的 CSV 交給司機，下載成功後清除該路線訂單。

**Why this priority**: 這是業主導入路線分組的核心目的 —— 讓備貨與出貨作業對齊實際車次。與 User Story 1 並列 P1，因為路線建立後若不能據以統計與結單，功能對使用者沒有實際產出。

**Independent Test**: 在已有路線與歸屬取貨點、且有既有訂單的前提下，選擇一條路線檢視統計交叉表與商品總量、匯出統計 CSV、再對該路線結單下載 CSV 並確認下載成功後訂單被清除。

**Acceptance Scenarios**:

1. **Given** 「A 線」含三個取貨點且各有訂單, **When** 管理員在路線訂單統計選擇「A 線」（日期區間預設今天）, **Then** 顯示「取貨點 × 商品」訂購數量交叉表，並附每個商品的總量。
2. **Given** 已顯示「A 線」統計, **When** 管理員匯出統計, **Then** 取得一份內容與畫面一致的 CSV。
6. **Given** 不選任何路線、日期區間維持預設今天, **When** 管理員查詢統計, **Then** 顯示今天有自取訂單的所有取貨點（跨路線、依顯示順序排列）× 商品的交叉表與各商品總量。
3. **Given** 「A 線」含多個取貨點的訂單, **When** 管理員對「A 線」結單, **Then** 取得一份涵蓋該路線所有取貨點訂單的 CSV，且 CSV 內每筆訂單可區分其所屬取貨點。
4. **Given** 對「A 線」結單時 CSV 下載成功, **When** 下載完成, **Then** 系統清除「A 線」上所有取貨點的訂單。
5. **Given** 對「A 線」結單時 CSV 下載失敗, **When** 下載未完成, **Then** 系統不清除任何訂單。

---

### User Story 3 - 以路線篩選訂單管理 (Priority: P2)

管理員在訂單管理頁以路線（含「未分路線」與「宅配」）作為主要篩選維度檢視訂單，其餘明細展開、結果內文字搜尋等行為照舊。

**Why this priority**: 提升日常訂單檢視的對齊度，但即使先沒有此篩選，統計與結單（P1）仍能交付核心價值；故列為 P2。

**Independent Test**: 在已有路線歸屬與訂單的前提下，於訂單管理頁切換不同路線（含未分路線、宅配）篩選，確認只列出對應路線的訂單，且明細展開與文字搜尋行為不變。

**Acceptance Scenarios**:

1. **Given** 訂單分屬多條路線、未分路線與宅配, **When** 管理員以「A 線」篩選, **Then** 僅列出「A 線」上各取貨點的訂單。
2. **Given** 有未指派路線之取貨點的訂單, **When** 管理員以「未分路線」篩選, **Then** 這些訂單全部列出。
3. **Given** 有宅配訂單, **When** 管理員以「宅配」篩選, **Then** 僅列出宅配訂單。
4. **Given** 已套用某路線篩選, **When** 管理員展開訂單明細或在結果內以文字搜尋, **Then** 行為與既有訂單管理一致。

---

### User Story 4 - 導覽與文案調整 (Priority: P3)

側邊欄新增「路線管理」入口；原「縣市訂單統計」更名為「路線訂單統計」，相關以縣市為主的文案改以路線描述。

**Why this priority**: 屬於可發現性與一致性的收尾，不影響核心作業能否完成，故列為 P3。

**Independent Test**: 開啟後台，確認側邊欄出現「路線管理」並可進入；確認統計頁標題與相關文案以「路線」呈現而非「縣市」。

**Acceptance Scenarios**:

1. **Given** 管理員登入後台, **When** 檢視側邊欄, **Then** 看到「路線管理」入口並可進入路線管理頁。
2. **Given** 管理員開啟原縣市統計頁, **When** 檢視標題與說明文字, **Then** 顯示「路線訂單統計」且文案以路線為主。

---

### Edge Cases

- 取貨點未指定路線時，於統計、訂單篩選、結單中一律歸入「未分路線」分組，且該分組可被選取、統計與結單。
- 路線改名後，所有引用該路線的後台檢視（統計選單、訂單篩選、結單清單）即時反映新名稱；既有取貨點歸屬不受改名影響。
- 對「未分路線」或「宅配」結單時，各自為獨立的一組，互不混入其他路線。
- 某路線目前沒有任何訂單時的統計與結單行為：統計顯示為空、結單不產生可清除資料（不應誤刪其他路線）。
- 訂單統計未選路線、僅指定日期區間時，列出該區間內所有有自取訂單的取貨點（跨路線），依顯示順序排序；同時指定路線與日期則取交集。
- 訂單統計清空日期且未選路線時，提示至少需指定路線或日期，不執行查詢。
- 取貨點顯示順序（以縣市分群）調整後，統計交叉表的取貨點列序依此（縣市內 sort_order）呈現；此排序同時供前台顧客選點使用。
- 刪除/改派取貨點到別條路線後，原路線的統計與結單範圍即時調整。
- 「未分路線」與「宅配」為系統內建分組，不可被當成一般路線新增、改名或刪除。

## Requirements *(mandatory)*

### Functional Requirements

**路線管理（R1）**

- **FR-001**: 系統 MUST 允許管理員新增送貨路線並指定名稱。
- **FR-002**: 系統 MUST 確保路線名稱唯一；新增或改名為既有名稱時 MUST 拒絕並提示名稱重複。
- **FR-003**: 系統 MUST 允許管理員為既有路線改名。
- **FR-004**: 系統 MUST 允許管理員刪除沒有任何取貨點歸屬的路線。
- **FR-005**: 當路線底下仍有取貨點時，系統 MUST 阻擋刪除並顯示清楚說明原因的錯誤訊息。

**取貨點歸屬路線（R2）**

- **FR-006**: 系統 MUST 允許為每個取貨點指定其所屬路線；一個取貨點 MUST 固定屬於且僅屬於一條路線。指派/調整所屬路線 MUST 於「路線管理」頁進行（可在該頁修改各路線底下及未分路線的自取點）；「自取點管理」頁對所屬路線 MUST 為唯讀顯示。
- **FR-007**: 尚未指定路線的取貨點，系統 MUST 在所有後台分組作業中將其歸入「未分路線」分組。
- **FR-008**: 取貨點的顯示順序（拖拉排序）MUST 維持以「縣市」分群——此排序供前台顧客選取貨點使用，不受路線影響；後台統計交叉表的取貨點列序依此順序（縣市內 `sort_order`）呈現。
- **FR-009**: 取貨點 MUST 保留其縣市/鄉鎮資訊（供前台選點、後台顯示與排序），並另以「所屬路線」屬性供後台分組；後台訂單統計/篩選/結單 MUST 以路線為分組依據而非縣市。

**路線訂單統計（R3）**

- **FR-010**: 訂單統計 MUST 支援兩個查詢條件——「路線」與「日期區間」——且兩者擇一必填（可只給其一，或同時給；同時給時取交集）。日期區間以訂單建立時間的台北時區（Asia/Taipei）日期判定、含起訖兩端。日期區間以「起」「訖」兩個日期欄位呈現，預設起＝訖＝今天（可改為任意區間）。若管理員清空日期且未選路線，系統 MUST 提示至少需指定路線或日期，且不執行查詢。
- **FR-011**: 統計 MUST 顯示「取貨點 × 商品」訂購數量交叉表：列＝取貨點（有選定路線時為該路線各取貨點；未選路線、僅以日期查詢時為該日期區間內有自取訂單的所有取貨點），依縣市內顯示順序（`sort_order`）排序；**商品欄位順序 MUST 依商品的顯示順序（`products.sort_order`）呈現**。
- **FR-012**: 統計 MUST 附上每個商品橫跨表內所有取貨點的總量，並 MUST 允許將目前統計結果（含套用之路線/日期條件）匯出為 CSV，內容與畫面一致。
- **FR-013**: 「未分路線」MUST 為訂單統計中可被選取的一條路線；其取貨點亦適用於日期查詢結果的歸類。

**訂單管理篩選（R4）**

- **FR-014**: 訂單管理頁 MUST 以路線作為主要篩選維度，篩選選項 MUST 包含各條路線、「未分路線」與「宅配」。
- **FR-015**: 套用路線篩選後，系統 MUST 僅列出該分組對應的訂單。
- **FR-016**: 訂單明細展開、結果內文字搜尋等其餘訂單檢視行為 MUST 維持與現況一致。

**路線結單（R5）**

- **FR-017**: 系統 MUST 支援以路線為單位結單：一條路線匯出成一份 CSV，涵蓋該路線上所有取貨點的訂單。
- **FR-018**: 結單 CSV 內每筆訂單 MUST 可區分其所屬取貨點。
- **FR-019**: 結單 MUST 維持既有兩階段流程：先成功下載 CSV，再清除該路線訂單；下載失敗時 MUST NOT 清除任何資料。
- **FR-020**: 「宅配」與「未分路線」MUST 各自為獨立可結單的一組，結單範圍不得混入其他分組。
- **FR-021**: 結單作業 MUST 維持各取貨點現場取貨號碼牌的既有規則不變。

**導覽與文案（R6）**

- **FR-022**: 側邊欄 MUST 新增「路線管理」入口。
- **FR-023**: 原「縣市訂單統計」MUST 更名為「路線訂單統計」，相關以縣市為主的後台文案 MUST 改為以路線描述。

**範圍與相容性約束**

- **FR-024**: 本功能 MUST NOT 更動前台顧客端 App 的縣市/鄉鎮選點機制與訂單寫入方式（含取貨號碼規則）。
- **FR-025**: 本後台對訂單與明細資料 MUST 僅進行讀取、匯出與清除，MUST NOT 寫入或修改訂單/明細內容。
- **FR-026**: 既有未指派路線的取貨點及其訂單 MUST 在「未分路線」分組中可被統計與結單，無需資料遷移即可運作。

### Key Entities *(include if feature involves data)*

- **送貨路線 (Delivery Route)**: 後台作業的分組單位，代表一趟固定車次。屬性：名稱（唯一）。一條路線可包含多個取貨點。「未分路線」與「宅配」為內建分組，非一般可增刪的路線。路線之間不需排序。
- **取貨點 (Pickup Spot)**: 既有實體，新增「所屬路線」關係（可為空 → 未分路線）與「路線內顯示順序」。保留既有縣市/鄉鎮等顯示資訊。每個取貨點固定屬於一條路線。
- **訂單 / 訂單明細 (Order / Order Item)**: 既有實體，由外部 App 寫入；本後台僅讀取、匯出、清除。訂單透過其取貨點關聯到路線；宅配訂單歸入「宅配」分組。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員能新增一條路線、把多個跨縣市取貨點指派給它，並在統計、訂單篩選、結單三項作業中都看到它們被視為同一組（100% 一致，無任何作業仍以縣市分組）。
- **SC-002**: 路線底下仍有取貨點時刪除嘗試 100% 被阻擋並提示原因；移除全部取貨點後刪除 100% 成功。
- **SC-003**: 路線訂單統計對所選「路線或日期區間」（兩者擇一必填、日期預設今天）正確顯示「各取貨點 × 各商品」數量與各商品總量，且可成功下載與畫面一致的 CSV。
- **SC-004**: 訂單管理以路線（含「未分路線」「宅配」）篩選時，列出的訂單與所選分組 100% 對應，無遺漏或誤列。
- **SC-005**: 對一條路線結單時，取得的單一 CSV 涵蓋該路線所有取貨點訂單且可區分各取貨點；訂單僅在 CSV 下載成功後被清除，下載失敗時清除筆數為 0。
- **SC-006**: 既有未指派路線的取貨點與其訂單 100% 出現在「未分路線」分組，並可被統計與結單，無需任何資料遷移步驟。
- **SC-007**: 前台顧客端選點與訂單寫入行為（含取貨號碼規則）在本功能上線前後無任何可觀察差異。

## Assumptions

- 「宅配」為既有的非取貨點配送類別，本功能將其視為與「未分路線」並列的獨立內建結單/篩選分組，沿用既有判定方式（不依賴取貨點所屬路線）。
- 既有取貨點在本功能上線時皆無所屬路線，因此自動歸入「未分路線」，毋須一次性資料遷移；管理員後續逐一指派。
- 路線之間不需排序（明確非目標）；僅路線「內」的取貨點顯示順序需可調整。
- 路線名稱唯一性比對採用既有後台慣例（區分大小寫與否未特別指定，採實作合理預設）；唯一性衝突時以明確訊息提示。
- 結單與統計的 CSV 欄位、編碼、檔名等格式沿用既有縣市結單/統計的慣例，僅將分組維度由縣市改為路線、並確保每筆訂單可標示所屬取貨點。
- 取貨點所屬路線改變或被刪除改派時，相關統計與結單範圍以查詢當下的歸屬為準（即時反映，無歷史快照需求）。
- 訂單統計的日期區間以訂單 `created_at` 的台北時區（Asia/Taipei）日期判定，區間含起訖兩端。
- 日期區間查詢僅適用於訂單統計（order-summary）；訂單管理篩選與結單分組不受日期影響，維持既有行為。
- 路線資料的維護權限與現有後台管理員權限一致（沿用既有 deny-by-default 授權，不新增角色）。
