# Feature Specification: 取貨號碼英數格式（站點代碼＋流水號）

**Feature Branch**: `008-pickup-code-format`

**Created**: 2026-07-10

**Status**: Draft

**Input**: User description: "修改取貨號碼邏輯，要變成英文+數字，例如:A1，且各站點不能重複"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 取貨號碼跨站點唯一且一眼可辨（英文＋數字） (Priority: P1)

現場發貨與核對時，每筆自取訂單的取貨號碼以「站點英文代碼＋流水號」呈現（例如 A1、A2、B1）。因為每個站點的英文代碼不同，任兩個站點之間的取貨號碼永遠不會相同——不再出現「板橋 1 號」與「中壢 1 號」同為「1」而混淆或錯領的情形。站點代碼由該站點的永久識別碼以固定規則換算而得，系統自動決定、永不變動，管理員無須維護。

**Why this priority**: 這是本功能的核心價值——消除跨站點撞號。沒有它，其餘顯示與匯出調整都失去意義。

**Independent Test**: 在兩個不同站點各建立一筆訂單，檢視訂單管理頁的取貨號碼：兩筆號碼的英文代碼不同、格式皆為「英文＋數字」，即可獨立驗證。

**Acceptance Scenarios**:

1. **Given** 站點甲（代碼 A）與站點乙（代碼 B）皆無未出貨訂單，**When** 兩站各成立第一筆自取訂單，**Then** 取貨號碼分別為「A1」與「B1」，兩者不同。
2. **Given** 站點甲已有 A1～A5 五筆未出貨訂單，**When** 該站再成立一筆訂單，**Then** 新訂單取貨號碼為「A6」。
3. **Given** 多筆訂單分屬不同站點，**When** 管理員在訂單管理頁檢視，**Then** 所有自取訂單的取貨號碼皆為「英文＋數字」格式，且任兩筆跨站點訂單號碼皆不相同。
4. **Given** 同一站點在極短時間內同時成立多筆訂單，**When** 系統指派號碼，**Then** 該站點內流水號仍不重複。

---

### User Story 2 - 清單、彙總與匯出一致採用新格式 (Priority: P2)

管理員在訂單管理、訂單彙總與下載的結單檔案（CSV／Excel）中看到的「取貨號」欄位，一律是新格式（如 A1）；以新格式關鍵字（如「A1」）搜尋訂單也能直接命中。發貨現場拿到的名單與後台畫面完全一致。

**Why this priority**: 號碼的價值在於現場核對；若匯出檔或搜尋仍是舊格式，現場人員將面對兩套號碼。

**Independent Test**: 建立跨兩站點的數筆訂單後下載結單檔，檢查「取貨號」欄皆為新格式且與畫面一致；於搜尋框輸入某筆的新格式號碼可找到該筆訂單。

**Acceptance Scenarios**:

1. **Given** 兩個站點各有未出貨訂單，**When** 管理員下載結單匯出檔，**Then** 「取貨號」欄顯示新格式號碼（如 A1、B3），與畫面顯示一致。
2. **Given** 存在取貨號碼「B3」的訂單，**When** 管理員以「B3」搜尋，**Then** 該筆訂單出現在結果中。
3. **Given** 一筆宅配訂單，**When** 檢視清單或匯出檔，**Then** 其取貨號欄維持現狀（宅配自身序列的純數字，不加站點代碼；因無英文開頭，與任何站點的新格式號碼不致混淆）。

---

### User Story 3 - 出貨清除後號碼重新起算 (Priority: P3)

某站點完成出貨、該分組訂單清除後，下一檔期該站點的取貨號碼重新從 1 起算（例如再次從 A1 開始），沿用既有的清帳歸零行為；站點代碼（英文部分）維持不變。

**Why this priority**: 維持既有營運節奏（每檔團購號碼歸零）；屬行為保留而非新能力。

**Independent Test**: 對某站點執行出貨清除後建立新訂單，確認號碼為「該站代碼＋1」。

**Acceptance Scenarios**:

1. **Given** 站點甲（代碼 A）出貨清除完畢，**When** 該站成立新檔期第一筆訂單，**Then** 取貨號碼為「A1」。

---

### Edge Cases

- 站點的永久識別碼超過 26 時，英文代碼進位為兩碼（第 27 站 → AA），號碼如「AA1」。
- 站點被刪除後其字母留空不回收（例如現存站點代碼為 A、B、E），字母不連續屬可接受現象。
- 上線當下已存在的未出貨訂單：直接以「所屬站點代碼＋其既有流水號」呈現，不重新編號、不影響已印出的任何內部序。
- 外部顧客端 App 建立的訂單：進入後台後同樣以新格式呈現，顧客端無須改版、下單不中斷。
- 宅配訂單無所屬站點：維持現狀——宅配有自己的一組流水號（純數字，不加站點代碼）；因所有站點號碼皆以英文開頭，宅配號碼與站點號碼不會混淆。
- 同站點併發下單：站點內流水號仍須唯一（沿用既有防撞規則）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每一自取站點 MUST 對應一個英文站點代碼，由該站點的永久識別碼以固定規則換算而得（1→A、2→B、…、26→Z、27→AA、依此類推）；代碼由系統決定、永不變動，不提供人工設定。
- **FR-002**: 自取訂單的取貨號碼 MUST 以「站點代碼＋流水號」形式呈現（如 A1）；流水號維持既有規則——於站點內自 1 遞增。
- **FR-003**: 任兩個不同站點之間的取貨號碼 MUST 不重複（由站點代碼互不相同保證）。
- **FR-004**: 同一站點內的流水號 MUST 不重複，包含多筆訂單同時成立的情形（沿用既有唯一性保證）。
- **FR-005**: 訂單管理、訂單彙總、結單匯出檔（CSV／Excel）等所有顯示取貨號碼之處 MUST 一致採用新格式。
- **FR-006**: 管理員以新格式關鍵字（如「A1」）搜尋訂單 MUST 能命中對應訂單。
- **FR-007**: 宅配訂單 MUST 維持既有取貨號碼行為與顯示（宅配自身序列的純數字），不套用站點代碼；站點號碼一律以英文開頭，故兩者不致混淆。
- **FR-008**: 外部顧客端 App 所建立的訂單 MUST 自動以新格式呈現；本變更 MUST NOT 要求顧客端 App 改版，且 MUST NOT 中斷其既有下單流程。
- **FR-009**: 上線時既有未出貨訂單 MUST 直接以新格式呈現（所屬站點代碼＋其既有流水號），不重新編號。
- **FR-010**: 出貨清除某分組後，該站點流水號 MUST 重新自 1 起算（維持既有清帳歸零行為）；站點代碼不變。

### Key Entities

- **自取站點（取貨點）**: 既有實體；新增一個「站點代碼」衍生屬性——由其永久識別碼以固定規則換算，非人工維護、非另行儲存的設定值。
- **訂單**: 既有實體；其站點內流水號維持不變，「取貨號碼」成為「所屬站點代碼＋流水號」的組合呈現。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一檔期內，跨站點取貨號碼重複的件數為 0。
- **SC-002**: 訂單清單、訂單彙總與結單匯出檔中，100% 的自取訂單取貨號碼以「英文＋數字」格式顯示，且三處顯示一致。
- **SC-003**: 上線前後外部顧客端 App 皆可正常下單，下單成功率無差異，且顧客端無須任何改版。
- **SC-004**: 管理員以取貨號碼搜尋任一自取訂單，一次輸入即可命中目標。

## Assumptions

- 「各站點不能重複」解讀為：取貨號碼於**所有站點之間**全域唯一（站點內唯一為既有行為，予以保留）。
- 站點代碼由站點永久識別碼換算（使用者已確認），不可自訂；站點刪除造成的字母跳號（如 A、B、E）為可接受現象。
- 站點永久識別碼超過 26 時，代碼進位為多字母（AA、AB…）。
- 宅配訂單維持現狀（宅配自身序列的純數字號碼，無站點代碼）；「未分路線」等分組概念與本功能無關，不受影響。
- 上線時既有未出貨訂單不重新編號，僅以新格式呈現。
- 外部顧客端 App 的任何修改不在本功能範圍；本功能以「顧客端無感」為前提設計。
