# Feature Specification: 商品多圖片與排序 (Product Image Gallery)

**Feature Branch**: `007-product-image-gallery`

**Created**: 2026-07-09

**Status**: Draft

**Input**: User description: "商品圖片要支援多張且有排序功能，且不能影響目前的資料"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 為商品新增多張圖片 (Priority: P1)

管理員編輯商品時，可以上傳一張以上的圖片（不再侷限於單張），全部保留供顧客瀏覽。

**Why this priority**: 多圖是本功能的核心價值——沒有它，其餘排序需求都無意義。

**Independent Test**: 編輯任一商品，上傳第二、第三張圖片並儲存，重新整理後確認所有圖片仍存在。

**Acceptance Scenarios**:

1. **Given** 商品目前只有一張圖片, **When** 管理員再上傳兩張圖片並儲存, **Then** 該商品共有三張圖片，且原本那張圖片內容不變。
2. **Given** 商品已有多張圖片, **When** 管理員移除其中一張並儲存, **Then** 該商品剩下其餘圖片，其餘圖片內容與相對順序不受影響。
3. **Given** 商品已有多張圖片, **When** 管理員刪除到只剩零張, **Then** 系統阻止儲存或提示商品至少需保留一張圖片（商品不可無圖）。

---

### User Story 2 - 調整圖片顯示順序 (Priority: P2)

管理員可以拖拉調整一個商品底下多張圖片的順序，第一張作為該商品的主要（封面）圖片。

**Why this priority**: 排序決定了顧客端看到的封面與瀏覽順序，是多圖功能能被實際運用的關鍵，但需先有多圖（P1）才有意義。

**Independent Test**: 對已有 3 張圖片的商品拖拉調整順序，儲存後重新整理，確認新順序（含新的第一張／封面圖）被保留。

**Acceptance Scenarios**:

1. **Given** 商品有多張圖片, **When** 管理員拖拉調整順序並儲存, **Then** 圖片以新順序永久保存，重新整理或重新登入後仍維持。
2. **Given** 已調整順序, **When** 顧客端或商品列表讀取該商品的「封面圖」, **Then** 讀到的是目前排序中的第一張圖片。

---

### User Story 3 - 既有圖片值不遺失、封面顯示不中斷 (Priority: P1)

功能上線後，所有既有商品原本的單張圖片值必須被完整搬入新的圖片集合、成為該商品的第一張（封面）圖片，不需管理員任何手動操作；封面圖在後台與顧客端持續正常顯示。

**Why this priority**: 既有圖片是不可重建的資產，遺失風險最高，故與 P1 並列最優先。註：本次一併更新顧客端 App 改讀新的圖片來源，故「既有讀取路徑保持不變」不再是限制；限制改為「既有圖片值不得遺失、封面顯示不得中斷」。

**Independent Test**: 在含既有商品的資料上套用遷移，任選一個從未被管理員編輯過圖片的既有商品，確認其原圖值已成為第一張（封面）圖片、後台列表與（已更新的）顧客端封面顯示正常，且商品筆數不變。

**Acceptance Scenarios**:

1. **Given** 功能上線前已存在、只有一張圖片的商品, **When** 套用遷移, **Then** 該商品的原圖值成為其圖片集合的第一張（封面），管理員無需操作。
2. **Given** 遷移將既有單圖搬入新結構後移除舊圖片欄, **When** 後台與已更新的顧客端讀取封面圖, **Then** 讀到的即該商品排序第一張，顯示與上線前一致（無圖片遺失或封面中斷）。

---

### Edge Cases

- 商品只有一張圖片時，不應顯示可拖拉排序的介面，或拖拉為無操作。
- 一次刪除多張圖片後嘗試儲存為零張：系統必須阻止並提示，不得儲存成功。
- 上傳圖片格式或大小不符規定：沿用既有圖片上傳的驗證規則與錯誤提示。
- 新增商品（非編輯既有商品）時未上傳任何圖片：沿用既有「商品必須有圖片」規則，阻止送出。
- 兩位管理員同時編輯同一商品的圖片與順序：以最後一次儲存為準（後寫覆蓋），與既有排序功能一致。
- 商品刪除時：其名下所有圖片（不只封面圖）都必須一併清除，不得留下孤兒圖片。
- 圖片數量上限：需有合理上限避免管理端與顧客端載入異常緩慢或版面失控。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 允許管理員為單一商品上傳、儲存一張以上的圖片。
- **FR-002**: 系統 MUST 讓管理員在編輯畫面中，以拖拉方式調整一個商品底下多張圖片的顯示順序。
- **FR-003**: 系統 MUST 永久儲存圖片的順序，使其在重新整理、重新登入後仍維持。
- **FR-004**: 系統 MUST 將排序後的第一張圖片視為該商品的封面／主要圖片，供既有僅顯示單張圖片的畫面（如商品列表、訂單品項）使用。
- **FR-005**: 系統 MUST 讓管理員在編輯畫面中移除商品的個別圖片，但 MUST 阻止移除到剩零張圖片。
- **FR-006**: 系統 MUST 在遷移時，為每個既有商品建立對應的「一張圖片」紀錄（沿用其既有圖片值），並將其設為排序第一，且不得改動該圖片本身的內容或位址（值原樣搬移）。
- **FR-007**: 遷移 MUST 先將既有商品圖片值完整搬入新結構，再移除舊圖片欄（expand-then-contract），確保無任何既有圖片值遺失；讀取封面圖的畫面（後台列表、隨本次一併更新的顧客端）在遷移後 MUST 持續正常顯示，不得出現圖片消失或封面中斷。
- **FR-008**: 系統 MUST 在商品被刪除時，一併清除該商品所有圖片（含其外部圖片儲存空間中的檔案），不得留下孤兒圖片。
- **FR-009**: 系統 MUST 對新上傳的每一張圖片套用既有的圖片格式與大小驗證規則。
- **FR-010**: 單次圖片順序或新增/移除的儲存 MUST 為全有或全無（atomic）——部分失敗時不得讓該商品的圖片集合處於順序缺漏或重複的狀態。
- **FR-011**: 系統 MUST 限制單一商品的圖片數量上限為 8 張。
- **FR-012**: 本功能對資料庫結構的異動 MUST 以獨立、可單獨套用的 migration 交付（不得直接改寫既有結構定義後就地覆蓋現況）。遷移 MUST 採 expand-then-contract：**先**新增圖片結構並將既有圖片值回填搬入，**確認搬移完成後**才移除舊的商品圖片欄；過程中不得遺失任何既有圖片值，亦不得刪除或破壞商品／訂單等其他既有資料列。移除舊欄後，仍讀取該欄的舊版顧客端會失效，故此遷移 MUST 與改讀新來源的後台＋顧客端同時上線。
- **FR-013**: 資料遷移 MUST 為可安全重跑或具明確一次性套用約定，若中途失敗 MUST 不留下部分套用、致既有資料處於毀損或不一致的狀態。

### Key Entities *(include if feature involves data)*

- **商品圖片 (Product Image)**: 新實體，隸屬於一個商品，具備圖片位址與「顯示順序」屬性（順序在同一商品的圖片間唯一、可比較，第一順位即為封面圖）。既有商品的既有單張圖片在上線時轉為此實體的第一筆紀錄。
- **商品 (Product)**: 既有實體，關聯至一組（一張以上）商品圖片。原本的「單一圖片」屬性於遷移後移除；封面改為衍生自其圖片集合中排序第一者（不再是商品自身欄位）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員可為單一商品成功儲存至少 5 張圖片並全部正確顯示。
- **SC-002**: 管理員拖拉調整圖片順序後，於 1 秒內看到新順序，重新整理後 100% 維持。
- **SC-003**: 遷移後，100% 既有商品的原有圖片維持可正常顯示（封面衍生自搬入的第一張），且商品列表等封面畫面與上線前一致。
- **SC-004**: 商品刪除後，該商品先前的所有圖片檔案 100% 從圖片儲存空間中移除，無孤兒檔案殘留。
- **SC-005**: 圖片新增／移除／排序儲存失敗時，商品圖片集合 100% 回復到操作前狀態，無半套（順序缺漏或重複）情形殘留。
- **SC-006**: 套用資料遷移後，商品筆數不變、既有圖片值 100% 搬入新圖片集合（無任何圖片值遺失）；除移除舊圖片欄外，不刪除或竄改其他既有商品／訂單資料。

## Assumptions

- 「不能影響目前的資料」解讀（本次已與使用者確認並調整）為：既有商品的圖片**值**不得遺失、封面呈現不得中斷。圖片值於遷移中原樣搬入新結構後，舊圖片欄即移除；因本次一併更新顧客端 App 改讀新來源，故不再要求「既有讀取路徑不變」。
- 圖片排序為**商品內部**排序（每個商品各自一組順序），與既有「商品排序」（商品彼此之間的順序，見 001-product-sorting）是不同層面的排序，互不影響。
- 低併發情境（少數管理員同時編輯同一商品的機率低），併發衝突以後寫覆蓋處理即可，與既有排序功能一致。
- 圖片上傳格式與大小限制沿用現行規則（JPG/PNG/WebP、5 MB 上限），不因多圖而放寬或收緊。
- 顧客端（外部 App，不在本 repo 範圍）本次一併更新為改讀新的圖片來源（`product_images` 或衍生封面），並與遷移同時上線，以避免舊版讀取已移除的商品圖片欄而失效。顧客端是否新增「瀏覽多圖」介面屬其自身範圍；本功能只保證新來源的封面／多圖資料正確可讀。
- 新增商品時，管理員至少需上傳一張圖片，此規則沿用現行「商品必須有圖片」的限制。
- 資料庫結構異動以獨立 migration 交付（置於既有 `db/migrations/` 慣例下），並同步更新 `db/schema.sql` 作為最新結構的真實來源；migration 於既有資料上手動套用，採 expand-then-contract（先回填搬移既有圖片值、再移除舊圖片欄），過程交易化＋冪等，不遺失既有圖片值、不動其他既有列（符合憲章 Development Workflow 與使用者「另外寫 migration」之要求）。
