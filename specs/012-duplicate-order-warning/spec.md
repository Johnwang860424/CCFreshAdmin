## Clarifications

### Session 2026-07-13

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立訂單前偵測同路線同名訂單並警示 (Priority: P1)

管理員在訂單管理頁使用「新增訂單」建立訂單。按下建立時，系統先檢查這筆新訂單所屬的路線分組（依取貨點推導的路線；宅配與未分路線視為各自獨立的分組）內，是否已存在客戶姓名相同的訂單。若存在，跳出警示視窗顯示「系統偵測到您可能已有訂單。請確認是否為重複下單」，由管理員決定「仍要建立」或「取消」；若不存在同名訂單，訂單直接建立，不出現任何跳窗。

**Why this priority**: 這是本功能的全部核心——在重複下單真正寫入之前攔下來提醒，避免事後才靠「重複下訂篩選」清理。

**Independent Test**: 在某路線已有客戶「王小明」的訂單。用新增訂單再替「王小明」建立同路線訂單，按建立時出現警示視窗；選「仍要建立」則訂單成立、選「取消」則回到表單。改用「李小華」建立則無跳窗直接成立。

**Acceptance Scenarios**:

1. **Given** 某路線分組內已有客戶「王小明」的訂單，**When** 管理員以相同姓名、同路線的取貨點新增訂單並送出，**Then** 顯示警示視窗，內容為「系統偵測到您可能已有訂單。請確認是否為重複下單」，且訂單尚未建立。
2. **Given** 警示視窗已顯示，**When** 管理員選擇「仍要建立」，**Then** 訂單照常建立，後續流程（成功訊息、取貨號顯示、列表刷新）與一般新增完全相同。
3. **Given** 警示視窗已顯示，**When** 管理員選擇「取消」，**Then** 不建立任何訂單，回到新增訂單表單且已填寫的內容保留，管理員可修改後重送。
4. **Given** 目標路線分組內沒有同名訂單，**When** 管理員送出新增訂單，**Then** 不顯示任何警示，訂單直接建立。
5. **Given** 同名訂單存在於「其他」路線分組，**When** 管理員在目前路線分組新增該姓名的訂單，**Then** 不顯示警示（僅比對同一分組）。
6. **Given** 同分組已有「王小明」的訂單，**When** 管理員輸入頭尾帶空白的「 王小明 」新增同分組訂單，**Then** 視為同名並顯示警示（輸入端去頭尾空白後比對；資料庫姓名由各寫入端保證已 trim）。
7. **Given** 管理員新增宅配訂單，**When** 宅配分組內已有同名訂單，**Then** 同樣顯示警示（宅配視為一個分組）；未分路線亦同。
8. **Given** 同分組內已有同名訂單多筆，**When** 管理員送出新增，**Then** 僅顯示一次警示視窗，確認後僅建立這一筆新訂單。

---

### Edge Cases

- **同名但不同分組**：不警示——比對範圍限於新訂單所屬的路線分組（路線／宅配／未分路線），與既有「重複下訂篩選」(011) 的視圖範圍一致。
- **姓名比對規則**：去除頭尾空白後完全相符；不做內部空白、全形/半形或別字正規化，電話不參與比對——與 011 的裁決一致。姓名於各寫入端（後台驗證與外部客購 App）均已去頭尾空白，資料庫內不存在帶空白的姓名，故查詢直接以完全相符比對。同名不同人會被警示，由管理員自行判斷後選「仍要建立」。
- **取貨點所屬路線為未分路線**：以「未分路線」分組比對。
- **警示為提示性質，非封鎖**：管理員確認後一律可建立；系統不自動擋單、不自動合併。
- **取消後重送**：表單內容保留；管理員修改姓名或取貨點後重送時重新檢查。
- **編輯訂單**：不在範圍內——僅「新增訂單」觸發檢查（編輯不能改姓名與取貨點）。
- **檢查與建立之間的空窗**：檢查以送出當下系統中的訂單為準；若兩位管理員幾乎同時替同一人建單，可能都未被警示——警示屬盡力提示，不保證絕對攔截。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 管理員送出「新增訂單」時，系統 MUST 先判定該筆訂單所屬的路線分組：取貨訂單依所選取貨點推導其路線，取貨點未分配路線者屬「未分路線」分組，宅配訂單屬「宅配」分組。
- **FR-002**: 系統 MUST 檢查該路線分組內現存（未出貨）訂單中，是否有客戶姓名與新訂單相同者；姓名比對以去除頭尾空白後的完全相符為準，電話不參與比對。
- **FR-003**: 偵測到同名訂單時，系統 MUST 在建立訂單前顯示警示視窗，內容 MUST 為「系統偵測到您可能已有訂單。請確認是否為重複下單」（警示語氣以視窗內建警示圖示呈現，文字不含 emoji），並提供「仍要建立」與「取消」兩個選擇。
- **FR-004**: 管理員選擇「仍要建立」時，系統 MUST 照常建立訂單，且結果（成功訊息、取貨號、列表刷新）與未觸發警示的新增流程完全一致。
- **FR-005**: 管理員選擇「取消」時，系統 MUST NOT 建立訂單，且 MUST 保留表單已填內容供修改後重送。
- **FR-006**: 未偵測到同名訂單時，系統 MUST 直接建立訂單，MUST NOT 顯示任何額外視窗或步驟。
- **FR-007**: 同分組內同名訂單無論多少筆，一次送出 MUST 只顯示一次警示視窗。
- **FR-008**: 檢查 MUST 為唯讀行為：偵測與警示本身不得改動任何訂單資料，也不得在既有訂單上留下標記。

### Key Entities

- **訂單（既有）**: 檢查時唯讀取用其客戶姓名與所屬取貨點／路線；本功能不新增、不修改任何儲存欄位。
- **路線分組（推導值）**: 由取貨點推導的路線，加上「宅配」「未分路線」兩個內建分組；僅作為比對範圍，不落地儲存。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同分組內存在同名（去頭尾空白後相符）訂單時，100% 在訂單建立前出現警示；不存在時 0% 出現警示、新增流程步驟數與現行完全相同。
- **SC-002**: 觸發警示後，管理員一次操作（按「仍要建立」或「取消」）即可完成決定，無需重新輸入表單內容。
- **SC-003**: 偵測到重複而管理員未確認前，0 筆訂單被寫入。
- **SC-004**: 警示啟用後，「重複下訂篩選」(011) 中出現的非故意重複訂單數量下降（管理員回報之誤建單較導入前減少）。

## Assumptions

- **範圍限於本後台的「新增訂單」流程**：外部客購 App 的下單流程不在本 repo 範圍，不受本功能影響；警示文字中的「您」沿用使用者指定的原文，實際閱讀者為代客建單的管理員。
- **跳窗文字以使用者原文為準**：「系統偵測到您可能已有訂單。請確認是否為重複下單」（2026-07-13 裁決：原文開頭的「⚠️」改由視窗內建警示圖示取代，文字不含 emoji）；描述中「如果沒有就直接建立訂單」理解為行為說明（無同名即直接建立），非跳窗文字的一部分。
- **姓名比對規則沿用 011 的裁決**：僅姓名（去頭尾空白後完全相符），電話不參與；不做模糊比對。
- **比對範圍為新訂單所屬的單一路線分組**：跨分組的同名訂單不警示，與 011 的視圖範圍一致。
- **警示視窗不列出既有訂單明細**：僅顯示指定文字與確認／取消；管理員如需比對細節，可取消後用既有的重複下訂篩選查看。
- **檢查母體為系統中該分組現存全部訂單**（含外部客購 App 建立者），非僅管理員畫面上已載入的資料。
