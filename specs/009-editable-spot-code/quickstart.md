# Quickstart: 站點代碼改為可維護欄位 — 驗證指南

> rev. 2026-07-11：回填改為依路線重編（放棄零感），驗證 1 隨之改寫；新增驗證 6（改分路線撞碼）。

## 前置

1. 於 Neon SQL Editor 執行 `db/migrations/006_add_pickup_spot_code.sql`（加欄位 → 依路線重編回填 → 上約束）。
2. `npm run dev`，以允許清單帳號登入後台。

## 驗證 1：依路線重編回填（SC-001 / FR-005）

1. Migration 前記下各路線的站點與其既有訂單流水號。
2. Migration 後於「自取點管理」頁檢查：每條路線內的站點代碼依站點建立順序為 A、B、C…；每條路線都從 A 起算；未分路線群組亦自 A 起算。
3. 訂單管理頁：既有訂單顯示「新代碼＋原流水號」（前綴改變、數字不變）；結單匯出檔一致。

## 驗證 2：代碼維護（FR-001/002/006，User Story 2）

於「自取點管理」頁：

- 表格出現「代碼」欄，值與驗證 1 的重編結果一致。
- 新增站點：不填代碼 → 擋（必填）；填「A1」「甲」→ 擋（格式）；填該路線未用過的「G」→ 成功，表格顯示 G。
- 編輯站點：改代碼為**同路線**已占用者（含小寫 `a`）→ 409「同路線已有相同代碼的站點」。
- 兩條不同路線各設一個「A」站 → 皆成功（跨路線允許同碼，FR-002）。
- 輸入小寫 `b` → 儲存後顯示大寫 `B`。

## 驗證 3：有訂單站點改碼警告（FR-007，User Story 2 情境 6）

1. 挑一個尚有訂單的站點（代碼 C），將代碼改為 D 送出。
2. 出現確認 Modal（提示既有 N 筆訂單取貨號將即時改變）；取消 → 代碼不變。
3. 再次送出並確認 → 儲存成功；訂單管理頁該站訂單由 C5 顯示為 D5，匯出檔一致。
4. 挑一個無訂單站點改碼 → 直接儲存、無 Modal。

## 驗證 4：號碼組成與宅配（FR-003/009，User Story 1）

1. 於代碼 K 的站點建立新訂單（後台建單或顧客端）→ 取貨號為 K＋站內下一號（如 K3）。
2. 宅配訂單 → 取貨號仍為純數字，不受影響。
3. 搜尋框輸入「k3」（小寫）→ 命中該筆訂單。

## 驗證 5：顧客端不中斷（FR-010 / SC-004）

- Migration 後由顧客端 App 下一筆自取單：成功寫入，後台以「站點代碼＋流水號」顯示。

## 驗證 6：改分路線撞碼（FR-008，User Story 2 情境 7）

1. 於「路線管理」頁，將代碼 A 的站點改分到已有 A 站的另一條路線 → 被擋，顯示「同路線已有相同代碼的站點」。
2. 先把其中一站代碼改掉（自取點管理頁）再移動 → 成功。
