# Feature Specification: 站點代碼改為可維護欄位（取貨號碼前綴）

**Feature Branch**: `009-editable-spot-code`

**Created**: 2026-07-11

**Status**: Draft

**Input**: User description: "修改取貨號碼邏輯：pickup_spots 表新增一個前綴代碼欄位（字母），取貨號改由該欄位＋流水號組成（取代目前由 pickup_spot_id 以 26 進位換算字母的做法）。後台可編輯站點的前綴代碼，既有站點需回填代碼。回填規則：同一路線（route_id）內依站點 id 順序編為 A、B、C…，每條路線都從 A 重新開始。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 取貨號碼改用站點自訂代碼組成（上線依路線重編） (Priority: P1)

自取訂單的取貨號碼（如 A1、B3）中的英文部分，改為取自該站點的「站點代碼」欄位——一個由管理員維護的字母代碼——而非由站點永久識別碼換算。上線時依「同路線內按站點建立順序編 A、B、C…（每條路線從 A 重新開始，未分路線自成一組）」回填所有既有站點；既有未出貨訂單的取貨號前綴會隨之改變為新代碼（流水號不變），現場以切換後畫面與匯出檔為準。

**Why this priority**: 這是本功能的核心——把號碼前綴的決定權從系統換算改為人工維護，並讓同路線站點的字母相鄰、每條路線都從 A 起算，方便現場按路線作業。

**Independent Test**: 上線（回填）後檢視訂單管理頁：每條路線內的站點代碼依序為 A、B、C…；既有訂單前綴皆為所屬站點的新代碼、流水號不變；清單與匯出檔一致。

**Acceptance Scenarios**:

1. **Given** 路線一有站點甲、乙（依建立順序），路線二有站點丙，**When** 本功能上線（回填完成），**Then** 甲＝A、乙＝B、丙＝A（每路線從 A 重編），未分路線的站點自成一組亦從 A 起算。
2. **Given** 站點乙回填後代碼為 B、其某筆既有訂單流水號為 5，**When** 上線後檢視該訂單，**Then** 取貨號顯示「B5」（前綴變更、流水號不變），清單、彙總、匯出檔三處一致。
3. **Given** 站點丁的站點代碼為 K，**When** 該站成立新自取訂單且站內流水號為 3，**Then** 取貨號碼顯示為「K3」。
4. **Given** 一筆宅配訂單，**When** 檢視清單或匯出檔，**Then** 其取貨號維持宅配自身序列的純數字，不受本變更影響。

---

### User Story 2 - 後台維護站點代碼 (Priority: P2)

管理員在自取點管理介面可以為站點設定或修改站點代碼：新增站點時必須填入代碼；編輯站點時可修改代碼。系統驗證代碼格式（純英文字母）並確保**同一路線內**（含「未分路線」群組）代碼不重複；不同路線之間允許相同代碼（例如每條路線都有自己的 A 站）。

**Why this priority**: 可維護性是本功能相對於既有換算制的新增價值；但沒有 P1 的組號切換，維護代碼無處生效。

**Independent Test**: 在自取點管理頁新增一個站點並填入該路線內未使用的代碼，再於該站建立訂單，確認取貨號以該代碼開頭；嘗試填入同路線已占用或含非字母字元的代碼時被阻擋並看到明確錯誤訊息。

**Acceptance Scenarios**:

1. **Given** 站點戊所屬路線內尚無站點使用代碼「G」，**When** 管理員將戊的代碼設為「G」，**Then** 儲存成功，該站新訂單取貨號以 G 開頭。
2. **Given** 同一路線內已有站點使用代碼「A」，**When** 管理員為該路線另一站點填入「A」（不分大小寫），**Then** 儲存被阻擋，並顯示同路線代碼重複的錯誤訊息。
3. **Given** 路線一與路線二各自尚無代碼「A」的站點，**When** 兩路線各有一站設為「A」，**Then** 皆儲存成功（跨路線允許同碼）。
4. **Given** 管理員輸入含數字或符號的代碼（如「A1」「甲」），**When** 送出，**Then** 儲存被阻擋，並提示代碼須為純英文字母。
5. **Given** 管理員以小寫輸入「b」，**When** 儲存，**Then** 系統以大寫「B」儲存與顯示。
6. **Given** 站點丙目前代碼為 C 且有未出貨訂單，**When** 管理員把代碼改為 D，**Then** 系統先顯示警告（既有未出貨訂單的取貨號將即時改變、可能與已通知顧客的號碼不符），管理員確認後才儲存；儲存後該站訂單如 C5 即顯示為 D5。
7. **Given** 站點己代碼為 A、欲從路線一改分到已有 A 站的路線二（路線管理頁），**When** 送出變更，**Then** 儲存被阻擋，提示目標路線已有相同代碼的站點，須先修改其中一站的代碼。

---

### Edge Cases

- 代碼比對不分大小寫：「a」與「A」視為相同，一律以大寫儲存與顯示。
- 唯一性範圍為「同路線內」：跨路線可能同時存在代碼 A 的站點，因而不同路線可能各有一筆「A5」訂單——此為使用者裁決接受的行為（現場按路線作業，路線內不撞號即可）。
- 「未分路線」視為一個獨立群組：群組內代碼不可重複，回填時亦自成一組從 A 起算。
- 上線回填會改變既有未出貨訂單的取貨號前綴（流水號不變）；上線後以新號碼為準，屬一次性轉換成本（使用者已知悉）。
- 同一路線站點超過 26 個時，回填代碼進位為兩碼（第 27 站 → AA）。
- 站點刪除即釋出其代碼，可供同路線新站點使用；已出貨檔期不留存資料，無歷史衝突。
- 站點改分路線時，若其代碼與目標路線既有站點重複，變更被阻擋（須先改碼）。
- 宅配訂單無站點，取貨號維持純數字；站點代碼必為英文字母開頭，兩者不致混淆。
- 外部顧客端 App 建立的訂單不受影響——App 只寫入訂單與站內流水號，代碼僅屬後台顯示組合。
- 取貨號搜尋、彙總、匯出與畫面顯示必須同步採用新的代碼來源，不得有一處仍用舊換算。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 每一自取站點 MUST 具有一個「站點代碼」屬性，由管理員維護；代碼為 1–3 個英文字母，一律以大寫儲存與顯示。
- **FR-002**: 站點代碼 MUST 於**同一路線內**唯一（不分大小寫；「未分路線」視為一個群組），系統於儲存時驗證並在重複時阻擋、提示明確錯誤；不同路線之間允許相同代碼。
- **FR-003**: 自取訂單的取貨號碼 MUST 以「該站點目前的站點代碼＋站內流水號」組成呈現；流水號規則維持不變。
- **FR-004**: 訂單管理、訂單彙總、結單匯出檔與取貨號搜尋 MUST 一致採用站點代碼欄位作為前綴來源，完全取代由永久識別碼換算的舊規則。
- **FR-005**: 上線時 MUST 為所有既有站點回填代碼：同一路線內依站點建立順序（永久識別碼遞增）編為 A、B、C…（超過 26 站進位為 AA…），每條路線自 A 重新起算，「未分路線」自成一組。既有未出貨訂單的取貨號前綴隨新代碼即時改變，流水號不變。
- **FR-006**: 新增站點時 MUST 要求填入站點代碼，未填或格式不符不得建立；與所屬路線（含未分路線）既有代碼重複時 MUST 阻擋。
- **FR-007**: 編輯站點時 MUST 可修改站點代碼；若該站點尚有未出貨訂單，系統 MUST 先顯示警告（說明既有訂單取貨號將即時改變），經管理員確認後才儲存（使用者已裁決：允許修改＋警告）。
- **FR-008**: 變更站點所屬路線時，若該站代碼與目標路線既有站點代碼重複，系統 MUST 阻擋並提示明確錯誤（須先修改代碼）。
- **FR-009**: 宅配訂單 MUST 維持既有行為（宅配自身序列的純數字取貨號），不套用站點代碼。
- **FR-010**: 本變更 MUST NOT 要求外部顧客端 App 改版，且 MUST NOT 中斷其既有下單流程。

### Key Entities

- **自取站點（取貨點）**: 既有實體；新增「站點代碼」為其可維護屬性（1–3 個大寫英文字母、同路線內唯一），取代原先由永久識別碼衍生的代碼。
- **訂單**: 既有實體；站內流水號不變，取貨號碼改為「所屬站點的站點代碼＋流水號」的即時組合呈現（非另行儲存）。
- **路線**: 既有實體；作為站點代碼唯一性的作用域（「未分路線」為內建群組）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 上線回填後，100% 站點的代碼符合「同路線內依建立順序 A、B、C…、每路線自 A 起算」；100% 既有自取訂單以「新代碼＋原流水號」顯示，清單、彙總、匯出檔三處一致。
- **SC-002**: 同一路線內代碼重複的儲存嘗試（含新增、改碼、改分路線）100% 被阻擋；同一路線內取貨號碼重複件數為 0。
- **SC-003**: 管理員可在自取點管理介面於 1 分鐘內完成一次站點代碼修改，且新代碼立即反映於後續號碼顯示。
- **SC-004**: 上線前後外部顧客端 App 下單成功率無差異，顧客端無須任何改版。

## Assumptions

- 代碼格式採 1–3 個英文字母（涵蓋單路線超過 26 站的進位情形），不含數字與符號；輸入不分大小寫、一律轉大寫。
- 代碼唯一性範圍為「同一路線內」（使用者已裁決）；跨路線同碼（進而跨路線同號如兩筆 A5）為可接受行為，因現場按路線分批作業。
- 「未分路線」（無所屬路線的站點）視為一個獨立的唯一性群組與回填群組。
- 上線回填會改變既有未出貨訂單的號碼前綴（使用者已知悉並接受，放棄「切換零感」）；流水號不變。
- 站點代碼於自取點管理介面（站點新增／編輯表單）維護；路線管理頁僅在「改分路線撞碼」時做阻擋提示，不提供改碼。
- 取貨號碼仍為即時組合顯示，訂單不另行快照代碼。
- 外部顧客端 App 的任何修改不在本功能範圍。
