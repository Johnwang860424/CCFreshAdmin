# Feature Specification: 訂單修改、刪除與出貨/CSV 分離

**Feature Branch**: `005-order-edit-ship`

**Created**: 2026-07-01

**Status**: Draft

**Input**: User description: "目前結單以後，消費者有可能追加品項，但目前版本沒有此功能，會導致後續品項要跟著下次結單一起購買，所以要改成以下需求。訂單管理頁面：支援修改訂單（可以新增或減少品項）、支援刪除訂單、結單功能不需下載 CSV（結單改為出貨、CSV 改成獨立按鈕）"

## Problem Statement

在目前版本中，一筆訂單一旦建立後便無法修改。當消費者在出貨前想追加或減少品項時，管理員只能請消費者「等下一檔」一起購買，造成消費者體驗不佳與作業困擾。此外，「結單」按鈕把「匯出 CSV」與「清除該分組訂單」綁在同一個動作，管理員無法在不清除資料的情況下單獨取得 CSV，也無法在不下載 CSV 的情況下完成清帳。

本功能讓管理員能在出貨前自由修改與刪除訂單，並將「匯出 CSV」與「清除訂單（出貨）」拆成兩個獨立動作。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 修改訂單品項（追加／減少） (Priority: P1)

管理員在訂單管理頁面針對某一筆既有訂單，開啟修改介面，新增商品明細、移除既有明細、或調整某明細的數量；儲存後訂單的總額隨之重新計算。這讓消費者在出貨前的「追加品項」需求可即時反映在同一筆訂單，不必併入下一檔。

**Why this priority**: 這是本次需求的核心動機——解決「結單後無法追加品項」的痛點。沒有它，其他改動無法達成商業目的。

**Independent Test**: 對一筆既有訂單新增一項商品並將另一項數量改為 2，儲存後展開訂單可見新明細、更新後的數量，且訂單總額等於各明細小計加總。

**Acceptance Scenarios**:

1. **Given** 一筆含 2 項明細的既有訂單，**When** 管理員新增一項商品（數量 1）並儲存，**Then** 訂單顯示 3 項明細，總額增加該項小計。
2. **Given** 一筆含 3 項明細的訂單，**When** 管理員移除其中一項並儲存，**Then** 訂單顯示 2 項明細，總額扣除被移除項的小計。
3. **Given** 一筆明細數量為 1 的訂單，**When** 管理員把該項數量改為 3 並儲存，**Then** 該項小計依其既有單價／促銷快照重新計算，訂單總額同步更新。
4. **Given** 修改介面中某明細數量被設為 0 或空白，**When** 管理員嘗試儲存，**Then** 系統阻擋並提示每項數量需為正整數。
5. **Given** 一筆訂單被修改到僅剩 0 項明細，**When** 管理員嘗試儲存，**Then** 系統阻擋並提示訂單至少需保留一項明細（如需清空請改用刪除訂單）。

---

### User Story 2 - 刪除單筆訂單 (Priority: P2)

管理員可針對訂單管理頁面清單中的任一筆訂單執行刪除；刪除前需二次確認。刪除後該訂單及其明細一併消失，不影響其他訂單。

**Why this priority**: 修改功能之外，管理員需要能處理取消／作廢的整筆訂單（例如消費者退單），這是完整訂單維護的一部分，但非核心追加情境。

**Independent Test**: 對清單中某一筆訂單按刪除並確認，該筆訂單自清單消失，重新載入後仍不存在，其他訂單數量與內容不變。

**Acceptance Scenarios**:

1. **Given** 某分組有 5 筆訂單，**When** 管理員刪除其中 1 筆並確認，**Then** 清單剩 4 筆，被刪除訂單不再出現。
2. **Given** 管理員按下刪除，**When** 確認對話框出現而管理員選擇取消，**Then** 訂單保留不變。
3. **Given** 一筆訂單被刪除，**When** 重新載入頁面，**Then** 該訂單與其明細皆不存在。

---

### User Story 3 - 出貨（清除）與 CSV 匯出分離 (Priority: P2)

原「結單」動作（匯出 CSV 後清除該分組訂單）拆成兩個獨立動作：

- 「出貨」：清除選定分組（依路線／未分路線／宅配）的所有訂單，**不再下載 CSV**。
- 「匯出 CSV」：獨立按鈕，僅下載該分組訂單的 CSV，**不清除任何資料**，可重複匯出。

**Why this priority**: 讓管理員能在需要時單獨保存 CSV、或在確認出貨後才清帳，兩者互不綁定，避免「想清資料就被迫下載檔案」或「想留檔就被迫清資料」。

**Independent Test**: 對某分組先按「匯出 CSV」取得檔案且訂單仍在；再按「出貨」確認後該分組訂單被清除，且此次未觸發任何檔案下載。

**Acceptance Scenarios**:

1. **Given** 某分組有訂單，**When** 管理員按「匯出 CSV」，**Then** 取得該分組 CSV 檔，且訂單清單筆數不變。
2. **Given** 某分組有訂單，**When** 管理員按「出貨」並確認，**Then** 該分組訂單全部清除，過程中未下載任何檔案。
3. **Given** 「出貨」為不可復原操作，**When** 管理員按下出貨，**Then** 系統先顯示不可復原之確認提示，需確認後才執行。
4. **Given** 某分組沒有任何訂單，**When** 管理員檢視動作，**Then** 該分組不提供可執行的出貨／匯出，或執行時提示無資料。

---

### Edge Cases

- 修改一筆含「已被刪除商品」明細（商品原始關聯已不存在）的訂單：該明細仍以名稱／單價快照顯示，可調整其數量或移除，但無法再對「已刪除商品」新增新明細（只能從現有商品挑選）。
- 兩位管理員同時操作同一筆訂單：其一已將訂單刪除或整組出貨後，另一人的修改／刪除應以「訂單不存在」友善提示，不得造成錯誤資料。
- 修改後總額為 0（例如全部明細皆為 0 元商品）：允許，總額可為 0，但明細數量仍須為正整數。
- 出貨清除後，同分組再建立的新訂單其取貨號碼牌自然重新自 1 起算（沿用既有清帳歸零行為）。
- 刪除單筆訂單不會回收其取貨號碼；同分組其餘訂單號碼保持不變（號碼可存在跳號，屬可接受）。

## Requirements *(mandatory)*

### Functional Requirements

**修改訂單**

- **FR-001**: 系統 MUST 允許管理員針對訂單管理清單中的任一筆既有訂單開啟修改介面。
- **FR-002**: 修改介面 MUST 允許管理員新增一或多項商品明細（自現有商品清單挑選並輸入數量）。
- **FR-003**: 修改介面 MUST 允許管理員移除既有明細。
- **FR-004**: 修改介面 MUST 允許管理員調整既有明細的數量。
- **FR-005**: 系統 MUST 驗證每項明細數量為正整數（≥1）；不符時阻擋儲存並提示。
- **FR-006**: 系統 MUST 要求訂單儲存後至少保留一項明細；若被清為 0 項則阻擋並提示改用刪除訂單。
- **FR-007**: 儲存修改後，系統 MUST 依最終明細重新計算並保存訂單總額（各明細小計之加總）。
- **FR-008**: 對「新增」的明細，系統 MUST 以該商品「目前」的單價與促銷設定計算小計快照並寫入該明細；既有未變動明細維持其原始單價／促銷快照。（見 Assumptions）
- **FR-009**: 對「調整數量」的既有明細，系統 MUST 以該明細既有的單價／促銷快照重新計算小計（不改用商品目前價格）。
- **FR-010**: 修改範圍 MUST 僅限商品明細；訂單的客戶姓名、電話、來源標籤、取貨方式、取貨點、宅配地址與備註於本功能中不可編輯（維持既有值），以避免變更取貨點時牽動取貨號碼牌重新指派。

**刪除訂單**

- **FR-011**: 系統 MUST 允許管理員刪除訂單清單中的單一筆訂單。
- **FR-012**: 刪除前系統 MUST 顯示二次確認；取消則不做任何變更。
- **FR-013**: 刪除一筆訂單 MUST 一併移除其所有明細，且不影響其他訂單。

**出貨與 CSV 分離**

- **FR-014**: 系統 MUST 將原「結單」入口更名為「出貨」。
- **FR-015**: 「出貨」MUST 依分組（路線／未分路線／宅配）永久清除該分組的所有訂單（沿用現行結單之清除語意，僅去掉 CSV 下載），且 MUST NOT 於此動作產生或下載 CSV；訂單資料模型不新增狀態欄位。
- **FR-016**: 「出貨」為不可復原操作，執行前 MUST 顯示不可復原之確認提示。
- **FR-017**: 系統 MUST 提供獨立的「匯出 CSV」動作，僅下載選定分組訂單的 CSV，MUST NOT 清除任何訂單，且可重複匯出。
- **FR-018**: 匯出的 CSV 內容 MUST 維持與現行結單相同的欄位（取貨號、客戶姓名、來源、取貨地點、購買清單、訂單總額、電話、備註）。

### Key Entities *(include if data involved)*

- **訂單 (Order)**：一筆消費者購買紀錄，含客戶資訊、取貨方式（自取／宅配）、取貨點、取貨號碼牌、備註與總額。本功能新增「可被管理員修改與刪除」的生命週期，直到該分組被出貨清除為止。
- **訂單明細 (Order Item)**：訂單下的單項商品購買，含商品名稱、單價、數量、促銷與小計之快照。本功能允許新增、移除與調整數量；小計依快照規則計算。
- **分組 (Group)**：出貨與 CSV 匯出的作用單位——每條路線一組、「未分路線」一組、「宅配」一組（沿用既有分組定義）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理員可在單一介面於 60 秒內完成一筆訂單的品項追加（新增一項並儲存），且訂單總額即時正確反映。
- **SC-002**: 消費者出貨前的追加需求 100% 可反映在原訂單，不需併入下一檔購買。
- **SC-003**: 管理員可在不清除任何訂單的情況下取得分組 CSV，且同一分組可重複匯出得到一致內容。
- **SC-004**: 「出貨」與「匯出 CSV」為兩個彼此獨立的動作；執行匯出不會清除資料、執行出貨不會下載檔案，兩者互不觸發對方。
- **SC-005**: 修改或刪除訂單後，重新載入清單所見資料與操作結果一致（無殘留、無誤刪其他訂單）。

## Assumptions

- **修改範圍僅限品項**（已確認）：依需求敘述「可以新增或減少品項」，修改介面只處理商品明細（新增／移除／改數量），不變更客戶／聯絡／取貨方式／取貨點等欄位（避免牽動取貨號碼牌重新指派）。
- **明細定價快照規則**：新增明細採「商品目前」的單價與促銷；既有明細維持原始快照，僅在改數量時以其既有快照重算小計。此規則兼顧「新增品項用現價」與「保留既有明細歷史金額」。
- **「出貨」沿用既有清除語意**（已確認）：「出貨」即現行結單之「永久清除該分組訂單」，僅移除 CSV 下載步驟。訂單資料模型不新增狀態欄位。
- **CSV 欄位與格式**：維持現行結單 CSV 的欄位與電話文字化處理，僅改為獨立、不清資料的按鈕。
- **取貨號碼牌**：修改品項不影響取貨號碼；刪除單筆訂單不回收號碼、不重編其他訂單號碼。
- **權限**：沿用現有管理後台登入與授權機制，僅授權管理員可修改／刪除／出貨／匯出。
- **資料一致性**：訂單與明細的寫入以既有原子化寫入方式處理，避免部分更新造成總額與明細不一致。
